# Palate Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship Palate on the shared core: onboarding into a flavor profile, a ranked menu with reasons and hard allergen blocks, table mode that merges palates, the chef card in the menu's language, and a stage view of the merged flavor map.

**Architecture:** Deterministic scoring in `web/src/lib/palate/score.ts` over an authored ingredient table; three demo menus shipped parsed; pasted menus parsed by `palate.menu`. **Tech Stack:** as core. Extra: none (OCR is out of scope tonight).

**Spec:** `docs/superpowers/specs/2026-09-12-palate-design.md`. Visual contract: `docs/mockups/index.html` §Palate.

### Task 1: Data and scoring

**Files:** `ingredients.json`, three menus, `score.ts`, `test/palate.score.test.ts`

**Interfaces (produces):**
```ts
export type Axes={coconut:number; smoky:number; sour:number; herbal:number; sweet:number; fermented:number}; // 0..1
export type Palate={axes:Axes; families:{label:string; count:number}[]; never:string[]; loved:string[]};
export type Dish={id:string; name:string; price?:number; description?:string; ingredients:string[]; section?:string};
export type Scored={dish:Dish; score:number; status:'ok'|'unknown'|'never'; reason:string; hits:string[]; blockedBy?:string};
export function dishVector(d:Dish):{axes:Axes; known:number; allergens:string[]}; // ingredient lookup by name/alias, mean of axes
export function scoreDish(p:Palate, d:Dish):Scored; // cosine(p.axes, dish.axes)*70 + familyOverlap*30 → 0..100; status rules per constraints; reason = top 2 shared axes/ingredients as "coconut · galangal"
export function rankMenu(p:Palate, dishes:Dish[]):Scored[];
export function mergeTable(ps:Record<string,Palate>, dishes:Dish[]):{everyone:{dish:Dish; scores:Record<string,number>; min:number}[]; splits:{dish:Dish; scores:Record<string,number>; spread:number; lowest:string}[]; blocked:{dish:Dish; by:string; allergen:string}[]};
// everyone: min ≥ 75 sorted by min desc; splits: spread ≥ 40; blocked: any member's never
```

Tests: massaman scores > 80 for a coconut-heavy palate; a sesame-containing dish is `never` for a sesame-never palate; house special is `unknown`; `mergeTable` puts massaman in `everyone` for three coconut palates and green curry in `splits` when one member scores it 24. ### Notes on what the plan asked for

- **Scoring.** `score = 70 · sharpen(cos(axes)) + 30 · familyCoverage`. Two cosines both landed in
  0.6–0.95 for every dish (non-negative vectors are never far apart), so the axis similarity is
  stretched onto 0..1 (`sharpen`, floor 0.30) and the family term became coverage — the share of the
  diner's family weight the dish actually contains — which reads as "how much of what you keep
  ordering is in this dish". Ranges are now 0–99 across a menu instead of 40–95.
- **`clear` on an unknown dish.** Per the plan, a dish with fewer than two known ingredients stays
  `unknown` after the kitchen answers; the answer is recorded and shown ("the kitchen says no
  sesame, but no ingredient record"). A dish blocked by an allergen *does* become scorable once the
  kitchen clears that allergen — the kitchen's answer is the record.
- **`?as=<id>&name=<name>&tone=<n>`** on any palate route opens the room as a named seat without
  touching the device identity. It is how one laptop drives three palates in the demo and how the
  screenshots above were taken.
- **`reasons`** is one batched `palate.reason` call per member per menu (top ten matches plus the
  grey and blocked rows), cached in room state under `reasons[memberId][dishId]` and invalidated
  when that member rebuilds their palate.
